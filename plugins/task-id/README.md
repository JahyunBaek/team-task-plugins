# task-id

작업 기록 번호를 **조회가 아니라 발급**으로 받는다.

## 무엇을 막는가

목록을 훑어 빈 번호를 고르는 방식에는 조회와 쓰기 사이에 틈이 있다. 두 세션이 같은 찰나에 같은 번호를 고르면 둘 다 통과한다. 워크트리를 갈라 병렬로 일하면 옆 세션이 아직 커밋하지 않은 파일은 아예 보이지 않는다. 다른 PC라면 더 그렇다.

이 플러그인은 번호를 고른 뒤 **원격에 그 번호 이름으로 ref 를 만든다.** 깃은 같은 이름의 ref 를 두 번 만들지 못하므로, "없을 때만 만들기"(`--force-with-lease=<ref>:`)로 밀면 같은 번호를 동시에 노린 세션 중 하나만 성공하고 나머지는 거절받는다. 거절받은 쪽은 다음 번호로 넘어간다. 판정을 원격이 하므로 다른 PC까지 덮인다.

ref 는 `refs/task-ids/<번호>` 에 쌓인다. 브랜치(`refs/heads/*`)나 태그(`refs/tags/*`) 와 나란한 별도 이름공간이다. `git notes` 가 `refs/notes/*` 를, 깃허브가 풀 리퀘스트를 `refs/pull/*` 에 두는 것과 같은 방식이다.

작업 폴더는 건드리지 않는다. ref 가 가리키는 것은 **빈 트리 위의 커밋 하나**(123바이트, 압축 전)이고, 메시지에 번호·프로세스·시각·난수를 적어 매번 다른 객체가 되게 한다. 같은 객체면 "방금 내가 잡은 것"과 "이미 있던 것"을 구별할 수 없기 때문이다.

`git branch` · `git tag` 목록에 나오지 않고, `clone` 할 때 따라오지도 않는다. 보려면 `git ls-remote origin "refs/task-ids/*"` 로 일부러 물어봐야 한다.

## 번호 등록부 — 원격 ref

원격의 ref(`refs/task-ids/*`)가 **번호 등록부**다. 브랜치가 달라도, PC 가 달라도 같은 등록부를 본다. 후보 번호는 세 곳에서 본 최대값 + 1 이다.

| | 어디를 보나 | 무엇을 막나 |
|---|---|---|
| 1 | 이 작업 트리의 작업 기록 파일 | |
| 2 | 형제 워크트리의 작업 기록 파일 | 옆 세션이 아직 커밋하지 않은 번호 |
| 3 | 원격의 ref 와 바닥 표시 | 다른 PC·다른 브랜치에서 받은 번호 |

ref 는 `/task-new` 로 받은 번호에만 생긴다. 플러그인을 쓰기 전에 만든 번호나 플러그인 없이 만든 번호는 **`/task-id-sync` 로 등록해 둬야** 한다(아래). 등록하지 않으면 실제로 겹친다 — 원격 dev 에 ref 없는 1~20번이 있고 체크아웃이 10번까지만 받은 상태에서 `0011`(이미 있는 번호)을 받았다.

### 특정 브랜치를 보지 않는 까닭

한때 넷째 근거로 원격 기본 브랜치(dev)에 커밋된 파일을 봤다. 그런데 작업 기록은 대부분 **기능 브랜치에서** 만들어지고, dev 에는 합쳐진 뒤에야 들어온다. 다른 브랜치에서 받은 번호는 dev 로 보이지 않는다.

이 플러그인을 쓰는 저장소에서 원격 브랜치 76개를 훑어 보니, 새 형식 번호 138개 가운데 **6개가 같은 번호에 서로 다른 문서**였다. 3개는 나중에 dev 에서 번호를 바꿨고, 3개는 dev 에 두 문서가 그대로 남아 있었다. 남은 3쌍은 각각 같은 날 dev 에 들어왔다 — 서로 다른 브랜치에서 같은 번호를 받고 각자 합친 모양이다.

모든 브랜치를 발급할 때마다 훑으면 그 저장소에서 약 5.5초가 걸린다(브랜치 목록 0.9초 + 파일 목록 4.7초). 그래서 브랜치를 보는 대신, 쓰인 번호를 **한 번 등록해 두고** ref 만 본다.

## 이미 쓰고 있는 번호 등록 — `/task-id-sync`

```
/task-id-sync            # 조회만 한다
/task-id-sync --apply    # 등록한다
```

보는 곳은 셋이다 — 원격의 **모든 브랜치**, 이 PC 의 **모든 로컬 브랜치**(푸시 전), **작업 트리와 형제 워크트리**(커밋 전). 찾은 번호 중 ref 가 없는 것을 "없을 때만 만들기"로 등록한다. 같은 번호에 다른 문서가 있으면 알리기만 한다. 다시 돌리면 이미 등록된 번호는 건너뛴다. 같은 트리는 한 번만 읽는다.

| 시험 저장소 | 결과 |
|---|---|
| 원격 브랜치 3 · 로컬 브랜치 5 · 워크트리 2 | 번호 8개 찾음 — 푸시 전 로컬 브랜치의 번호, 커밋 전 문서의 번호까지 |
| 두 기능 브랜치가 같은 번호를 씀 | 중복 1건으로 알림 |
| `--apply` | 8개 등록 · 다시 돌리면 등록할 것 0 |
| 등록 뒤, 5번까지만 받은 체크아웃이 발급 | `0009` (원격 등록 최대 8 + 1) |

언제 부르나:

- 플러그인을 처음 붙일 때 저장소에 한 번
- 팀원이 플러그인을 설치한 뒤 **자기 PC 에서 한 번** — 아직 푸시하지 않은 브랜치와 커밋 전 문서의 번호가 등록된다
- 플러그인 없이 만든 번호가 생겼을 때 (훅이 「선점하지 않고 새 작업 기록을 만들었습니다」 라고 알린 경우)

## 설치

```bash
claude plugin marketplace add https://github.com/JahyunBaek/team-task-plugins
claude plugin install task-id@team-task-plugins
```

**자동 업데이트** — Anthropic 공식이 아닌 마켓플레이스는 자동 업데이트가 기본으로 꺼져 있다. 저장소 `.claude/settings.json` 의 `extraKnownMarketplaces` 항목에 `"autoUpdate": true` 를 두면(`/plugin` → Marketplaces → Enable auto-update 가 쓰는 자리와 같다) 세션에서 첫 메시지 뒤 최대 10분 안에 새 판을 받는다. 적용은 `/reload-plugins` 나 다음 실행 — 재시작은 필요 없다. 새 판은 `plugin.json` 의 `version` 으로 알아보므로 배포할 때마다 버전을 올린다.

```json
"extraKnownMarketplaces": {
  "team-task-plugins": {
    "source": { "source": "git", "url": "<저장소 주소>.git" },
    "autoUpdate": true
  }
}
```

깃허브가 아닌 git 호스트에 올렸다면 **주소 끝에 `.git` 을 붙인다.** 안 붙이면 CLI 가 git 저장소가 아니라 JSON 파일 주소로 보고 HTTP 로 받으려 한다. AWS 코드커밋 주소가 그렇다 — `.../v1/repos/<이름>` 그대로 넣으면 `HTTP 401 error while downloading marketplace` 로 실패하고, `.../v1/repos/<이름>.git` 으로 넣으면 clone 으로 받는다.

## 쓰는 법

```
/task-new <도메인> <이름>
```

발급된 번호로만 파일을 만든다. 결과의 `attempts` 가 2 이상이면 그 사이 다른 세션이 번호를 채갔다는 뜻이다.
`verified: true` 가 붙으면 push 는 시간 초과·오류로 끝났지만 원격에 이 PC 가 민 그대로 잡혀 있어 발급한 것이다.
`recovered` 가 붙으면 지난번 「확인 대기」 로 끝난 번호가 그 뒤 원격에 이 PC 것으로 나타난 것이다(아래 「발급이 실패로 보고됐는데 원격에 번호가 생기는 경우」).

```json
{"ok":true,"id":"TASK-2026-core-0042","attempts":2,"path":"docs/tasks/core/TASK-2026-core-0042-...md","scanned":{"worktrees":1,"remote":true}}
```

| 인자 | 하는 일 |
|---|---|
| `--dry-run` | 선점하지 않고 "지금 받으면 나올 번호"와 근거별 최대값만 본다. 원격에 아무것도 쓰지 않는다 |
| `--adopt <번호>` | 이 PC 에서 쓰던 번호 하나를 원격에 등록한다 (여러 개는 `/task-id-sync`) |

`--adopt` 는 이 PC 의 작업 트리(형제 워크트리 포함)에 그 번호의 문서가 있을 때만 등록한다.

| 상황 | 결과 |
|---|---|
| 아직 등록되지 않은 번호 | 등록한다 (원격에 ref 1개) |
| 원격에 이미 등록됨 | 등록하지 않고 알린다 — 같은 번호로 다른 문서가 있는지는 ref 만 보고는 모른다 |
| 원격에 이미 등록됐는데 ref 를 만든 사람이 지금 git 사용자(`user.email`) | 이 PC 기록에 올린다(`recovered: true`) — 발급이 실패로 보고됐지만 실제로 잡혔던 번호다(0.2.2) |
| 이 PC 에 그 번호의 문서가 없음 | 멈춘다 |
| 그 사이 다른 세션이 먼저 등록 | 멈춘다 — 번호를 다시 받아야 한다 |

## 설정

저장소 루트에 `.task-id.json` 을 두면 바뀐다.

| 키 | 기본값 | 뜻 |
|---|---|---|
| `taskDir` | `docs/tasks` | 작업 기록이 쌓이는 폴더 |
| `refNamespace` | `refs/task-ids` | 번호 등록부(ref)를 두는 이름공간 |
| `remote` | `origin` | 판정을 맡길 원격 |
| `digits` | `4` | 번호 자릿수 |
| `offlinePolicy` | `block` | 원격을 못 볼 때 — `block`(중단) 또는 `warn`(경고 후 잠정 발급) |
| `maxAttempts` | `25` | 거절당했을 때 다음 번호로 넘어가는 최대 횟수 |
| `pushTimeoutMs` | `60000` | 선점 push 를 기다리는 시간(0.2.1 까지 15초 고정). 넘기면 원격을 다시 묻는다(아래) |
| `defaultBranch` | (자동) | 정리(`/task-id-prune`)가 "합쳐진 번호"를 판단하는 기준 브랜치. 예: `refs/heads/dev` |
| `pruneKeep` | `20` | 정리할 때 개별 ref 를 남겨 두는 최근 번호 개수 |

## 구성

| 조각 | 하는 일 |
|---|---|
| `/task-new` 커맨드 | 번호를 선점하고 발급한다 |
| `/task-id-sync` 커맨드 | 이미 쓰고 있는 번호를 등록부에 등록한다. 기본은 조회만 한다 |
| `guard` 훅 (PostToolUse) | **새로 만든** 작업 기록 파일만 본다. 폴더와 번호의 도메인이 다를 때, 같은 번호의 문서가 이 트리·형제 워크트리에 있을 때, 원격에 이미 등록된 번호일 때(그 ref 를 만든 사람이 지금 git 사용자면 `--adopt` 를 안내), `/task-new` 로 받은 번호가 아닐 때 알린다. 막지 않는다. 저장소는 세션 폴더가 아니라 **파일 위치**로 찾는다 — 세션은 주 저장소이고 파일은 워크트리 안일 때도 본다. 경고는 JSON 으로 내서 Claude 의 문맥(`additionalContext`)과 화면(`systemMessage`)에 같이 뜬다 — PostToolUse 훅이 종료 코드 0 으로 낸 표준 출력은 디버그 로그에만 남는다(0.2.0 까지는 이 때문에 경고가 아무에게도 보이지 않았다) |
| `/task-id-prune` 커맨드 | 쓸모를 다한 ref 를 원격에서 정리한다. 기본은 조회만 한다 |
| `task-id` 스킬 | 규칙과, 거절·망 끊김 때의 행동 |

훅 경고가 Claude 에게 가는지는 실제 세션으로 확인했다(2026-10-02). `claude -p --plugin-dir` 로 선점 없이 작업 기록을 쓰게 하면
0.2.0 은 Claude 가 경고를 받지 못했고(세션 기록에도 없음), 0.2.1 은 화면에 `PostToolUse:Write says: [task-id] …` 가 뜨고 Claude 가 경고를 그대로 인용했다.

## 발급이 실패로 보고됐는데 원격에 번호가 생기는 경우 (0.2.2 에서 고침)

0.2.1 까지는 선점 push 가 **시간 초과(15초)나 연결 끊김**으로 끝나면 원격을 확인하지 않고 「선점에 실패했습니다」 를 돌려줬다.
그런데 그 push 는 원격에서 끝났을 수 있다 — Windows 에서는 시간 초과로 `git.exe` 만 죽고, 전송하는 자식 프로세스는 살아서 push 를 마저 끝낸다.
서버가 반영한 뒤 응답만 끊긴 경우도 같다. 그러면

- 원격에는 그 번호의 ref 가 생기고, 이 PC 의 발급 기록(`task-id-claims.json`)에는 없다.
- 다시 발급하면 다음 번호가 나오고 앞 번호는 **문서 없는 빈 번호**로 남는다.
- 그 빈 번호로 문서를 만들면 훅이 「원격에 이미 등록된 번호 — 다른 세션의 번호」 라고 경고한다.

0.2.2 는 push 가 실패하면 **메시지 글자가 아니라 원격 상태로 판정**한다. 선점용 객체는 매번 다르게 만들기 때문에(번호·프로세스·시각·난수) 원격 ref 가 내 객체인지 알 수 있다.

| 원격의 그 ref | 판정 |
|---|---|
| 내가 민 객체 그대로 | 잡은 것 — 발급한다(`verified: true`) |
| 다른 객체 | 다른 세션이 먼저 잡았다 — 다음 번호 |
| 없음 | 정말 실패 — 이유를 그대로 알린다 |
| 시간 초과 직후 아직 없음 · 원격 조회도 실패 | 「확인 대기」 로 기록하고 실패로 알린다(`pending: true`). 다음 발급 때 원격에 내 객체가 나타났으면 `recovered` 로 알리고 기록을 확정한다. 훅도 그 번호를 이 PC 것으로 본다 |

시간 초과·연결 끊김처럼 거절 문구가 없을 때는 늦게 끝나는 push 를 기다리며 0·2·5초에 다시 묻는다. 기다리는 시간 자체도 `pushTimeoutMs`(기본 60초)로 늘렸다.

이미 생긴 빈 번호(0.2.1 이전)는 `/task-new --adopt <번호>` 로 이 PC 기록에 올릴 수 있다 — ref 를 만든 커밋의 작성자 메일이 지금 `user.email` 과 같을 때만 올린다.
훅도 그런 번호에는 「다른 세션의 번호」 대신 「이 PC 의 git 사용자가 잡은 번호 — `--adopt` 로 기록에 올리라」 고 알린다.

로컬 bare 저장소를 원격 삼아 서버 훅으로 재현했다(2026-10-08, Windows · git 2.54 · node 24).

| 상황 | 0.2.1 | 0.2.2 |
|---|---|---|
| ref 는 바로 생기고 응답이 늦음(post-receive 20초 / 0.2.2 는 `pushTimeoutMs` 1.5초에 4초) | `선점에 실패했습니다: spawnSync git ETIMEDOUT`(15.5초) · 원격엔 0001 · 기록 없음 | `verified: true` 로 0001 발급(2.4초) · 기록에 sha |
| 서버가 10초 붙잡은 뒤에야 ref 를 씀(`pushTimeoutMs` 1.5초) | — | 실패 + `pending: true`(9.5초). 6초 뒤 원격에 0001 이 나타남(죽은 git 의 자식이 마저 끝냄). 다음 발급에서 0002 와 함께 `recovered: [0001]` |
| 서버 훅이 거절(번호 안 생김) | 「거절」 문구를 「남이 잡음」 으로 보고 25번 넘어가다 `25번 시도했지만…`(27.9초) | 바로 실패 · 「원격에 이 번호는 만들어지지 않았습니다」(1.4초) |
| 같은 순간 두 발급(서버 1초 지연) | — | 0001(1회) · 0002(2회) — 겹침 없음 |
| 같은 사용자가 원격에 잡았지만 이 PC 기록에 없는 번호로 문서 작성 → `--adopt` | 「다른 세션의 번호」 경고 · `--adopt` 는 「이미 등록됨」 | 「이 PC 의 git 사용자가 잡은 번호 — `--adopt`」 경고 · `--adopt` 가 기록에 올림(`recovered: true`) · 이후 경고 없음 |
| 다른 사용자가 잡은 번호로 문서 작성 | 「다른 세션의 번호」 | 같다 |

## 발급은 브랜치를 내려받지 않는다

발급이 원격에 묻는 것은 ref 목록과 선점 두 가지뿐이다. 원격 브랜치를 내려받지 않는다.

dev 를 넷째 근거로 보던 판에서는 그 파일 목록을 보려고 `git fetch` 를 했는데, 여러 세션이 동시에 발급하면 추적 브랜치(`refs/remotes/origin/dev`)를 갱신하다 잠금끼리 부딪혔다. 끝 커밋만 받아 오게 고쳤고, 브랜치를 보지 않게 된 뒤로는 fetch 자체가 없다.

| dev 를 움직이며 동시에 발급 | 성공 | 실패 | 겹친 번호 |
|---|---|---|---|
| 평범한 `git fetch` (6개씩 5번, 30회) | 9 | 21 (`cannot lock ref`) | 0 |
| 끝 커밋만 받아 오기 (30회) | 30 | 0 | 0 |
| 브랜치를 보지 않음 — 0.2.0 (6개씩 5번, 30회) | 30 | 0 | 0 |
| 브랜치를 보지 않음 — 0.2.0 (8개 동시) | 8 | 0 | 0 |

0.2.0 의 30회는 첫 줄과 같은 조건이다. 시도 횟수는 1~6회가 각각 5번이었고, `refs/remotes/origin/dev` 는 그대로였다.

## 기준 브랜치 (정리에서만 쓴다)

정리는 "파일이 기준 브랜치에 합쳐진 번호"의 ref 만 지운다. 원격이 기본 브랜치를 알려주면 그것을 쓰는데, **코드커밋은 알려주지 않는다.**

```
깃허브:    ref: refs/heads/main	HEAD
코드커밋:  8f669ad...	HEAD          ← ref: 줄이 없다
```

그때는 로컬에 적힌 `origin/HEAD`, 그래도 없으면 HEAD 해시와 일치하는 브랜치를 쓴다. 다 실패하면 정리를 멈추고 설정하라고 알린다. 작업이 기본 브랜치가 아닌 곳(예: `dev`)에 합쳐지면 못박아 둔다.

```json
{ "defaultBranch": "refs/heads/dev" }
```

## 맞바꿈

- 발급할 때마다 원격을 탄다(ref 목록, 선점). **원격을 못 보면 번호를 주지 않고 멈춘다**(기본값 `block`).
  다른 PC 가 무슨 번호를 잡았는지 모르는 상태이기 때문이다. 어차피 그 상태에서는 작업을 푸시하지도 못한다.
  정말 끊긴 채로 받아야 하면 `offlinePolicy` 를 `warn` 으로 두면 근거 1·2 만으로 **잠정** 번호를 준다.
- 등록부는 ref 다. 플러그인 없이 만든 번호는 `/task-id-sync` 로 등록하기 전까지 다른 PC 에 보이지 않는다.
- 선점해 놓고 문서를 쓰지 않으면 그 번호는 빈다.
- 발급 기록(`task-id-claims.json`)은 워크트리끼리 함께 쓰는 자리(`git rev-parse --git-common-dir`)에 둔다. 다른 PC 와는 나누지 않는다 — 다른 PC 와의 판정은 원격 ref 가 맡는다.
- ref 는 저절로 지워지지 않는다. `/task-id-prune` 으로 정리하는데, 손으로 불러야 한다.

## ref 정리

```
/task-id-prune              # 조회만 한다
/task-id-prune --apply      # 실제로 지운다
/task-id-prune --keep 0 --domain core --apply
```

정리는 **파일이 기준 브랜치에 합쳐진 번호의 ref 만** 지운다. 지울 때 그룹(연도·도메인)마다 **"여기까지는 이미 쓰였다"** 를 ref 이름에 적어 하나 남긴다.

```
refs/task-ids/_floor/TASK-2026-cm-0020
```

발급은 이 번호도 읽는다(근거 3). 등록부가 ref 이므로, ref 를 지우고 바닥 표시를 남기지 않으면 그 번호들이 다시 풀린다. **바닥 표시를 먼저 세우고 나서 지운다** — 순서가 바뀌면 그 사이가 빈다. 바닥 표시를 세우지 못한 그룹은 지우지 않는다.

바닥 표시를 넣기 전에는 정리 뒤에 뒤처진 체크아웃이 `0011`(이미 있는 번호)을 받는 것을 재현했다. 넣은 뒤 같은 상황에서 `0021`, 21~30 을 커밋하고 다시 정리한 뒤 `0031` 을 받았다. 두 번째 정리에서 바닥 표시는 0020 → 0030 으로 올라가고 옛 표시는 지워졌다.

**지우지 않는 것이 두 가지다.**

- **파일이 아직 기준 브랜치에 없는 번호** — 기능 브랜치에서 진행 중인 번호다. 지우면 그 번호가 다시 풀린다.
- **최근 `pruneKeep` 개**(기본 20) — 여유분이다. `--keep 0` 이어도 안전하다.

정리하고 나면 그룹마다 ref 가 바닥 표시 하나로 줄어든다. 20개를 정리했을 때 원격에는 `_floor/TASK-2026-cm-0020` 하나만 남았다.

### 용량 이야기는 기대하지 않는 게 좋다

실측값이다. 작업 기록 파일 30건이 커밋된 저장소에 ref 33개를 만들어 두고 29개를 지웠다.

| | 값 |
|---|---|
| 원격 저장소 크기 | 35,317 → 34,543 바이트 (774바이트 줄었다) |
| ref 하나당 | 약 27바이트 |
| ref 가 가리키는 커밋 객체 | 123바이트 (압축 전) |
| 목록에 찍히는 한 줄 | 73바이트 |

**500개를 모아도 13KB다.** 줄어드는 쪽은 발급할 때마다 읽어 오는 목록 길이인데 그것도 500개면 36KB다. 아래 표의 Gerrit 은 252,633개를 달고 돌아간다. 정리는 깔끔함을 위한 것이고 용량 때문이 아니다.

## 이 방식이 안전한 근거

깃 공식 문서(`git update-ref`)가 "없을 때만 만들기"를 보장한다.

> 생성하려는 ref 가 존재하지 않음을 보장하려면 `<old-oid>` 에 40개의 "0" 또는 빈 문자열을 지정할 수 있다

같은 문서에 *"각 ref 는 개별적으로 원자적으로 갱신되거나 삭제된다"* 고 적혀 있다.

평범한 `git push` 도 이미 있는 ref 를 대개 거절하지만 이유가 다르다. 평범한 push 는 "새 커밋이 기존 커밋의 자손이 아니라서" 거절하고, `--force-with-lease=<ref>:` 는 "그 ref 가 존재해서" 거절한다. 새 커밋이 기존 커밋의 자손이면 평범한 push 는 덮어쓴다. 실제로 A 가 잡은 ref 에 A 의 자손 커밋을 밀었더니 평범한 push 는 B 로 바꿨고, `--force-with-lease=<ref>:` 는 `stale info` 로 거절해 A 를 지켰다.

## 이렇게 쓰는 곳들

`refs/` 밑에 자기 칸을 파는 것은 흔한 방식이다. 공개 저장소를 직접 조회한 결과다(2026-10-01).

| 저장소 | 자기 칸 | 개수 | 브랜치 |
|---|---|---|---|
| [Gerrit](https://gerrit.googlesource.com/gerrit) | `refs/changes/*` | 252,633 | 58 |
| [GitLab](https://gitlab.com/gitlab-org/gitlab-foss) | `refs/environments/*` · `refs/merge-requests/*` | 44,034 · 950 | 4,469 |
| [GitHub](https://github.com/anthropics/claude-plugins-official) | `refs/pull/*` | 5,142 | 718 |
| [git-bug](https://github.com/git-bug/git-bug) | `refs/bugs/*` · `refs/identities/*` | 454 · 312 | 33 |

깃 자체도 그렇다. `git notes` 는 `refs/notes/*`, `git stash` 는 `refs/stash` 를 쓴다.

**선점 용도로 쓴 사례도 있다.** [Backlog.md 의 제안](https://github.com/MrLesk/Backlog.md/issues/937)은 여러 사람이 같은 작업을 동시에 집는 문제를 `refs/backlog/tasks/*` 와 `--force-with-lease` 로 푼다. 목표를 *"동시 선점자는 정확히 한 명"* 으로 적고 있다. 다만 그쪽은 원격을 못 볼 때 **막는 쪽**을 택했고, 이 플러그인도 같은 선택을 기본값으로 둔다.
