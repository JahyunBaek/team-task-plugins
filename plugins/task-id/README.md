# task-id

작업 기록 번호를 **조회가 아니라 발급**으로 받는다.

## 무엇을 막는가

목록을 훑어 빈 번호를 고르는 방식에는 조회와 쓰기 사이에 틈이 있다. 두 세션이 같은 찰나에 같은 번호를 고르면 둘 다 통과한다. 워크트리를 갈라 병렬로 일하면 옆 세션이 아직 커밋하지 않은 파일은 아예 보이지 않는다. 다른 PC라면 더 그렇다.

이 플러그인은 번호를 고른 뒤 **원격에 그 번호 이름으로 ref 를 만든다.** 깃은 같은 이름의 ref 를 두 번 만들지 못하므로, "없을 때만 만들기"(`--force-with-lease=<ref>:`)로 밀면 같은 번호를 동시에 노린 세션 중 하나만 성공하고 나머지는 거절받는다. 거절받은 쪽은 다음 번호로 넘어간다. 판정을 원격이 하므로 다른 PC까지 덮인다.

ref 는 `refs/task-ids/<번호>` 에 쌓인다. 브랜치(`refs/heads/*`)나 태그(`refs/tags/*`) 와 나란한 별도 이름공간이다. `git notes` 가 `refs/notes/*` 를, 깃허브가 풀 리퀘스트를 `refs/pull/*` 에 두는 것과 같은 방식이다.

작업 폴더는 건드리지 않는다. ref 가 가리키는 것은 **빈 트리 위의 커밋 하나**(123바이트, 압축 전)이고, 메시지에 번호·프로세스·시각·난수를 적어 매번 다른 객체가 되게 한다. 같은 객체면 "방금 내가 잡은 것"과 "이미 있던 것"을 구별할 수 없기 때문이다.

`git branch` · `git tag` 목록에 나오지 않고, `clone` 할 때 따라오지도 않는다. 보려면 `git ls-remote origin "refs/task-ids/*"` 로 일부러 물어봐야 한다.

## 번호를 정하는 근거

후보 번호는 네 곳에서 본 최대값 + 1 이다.

| | 어디를 보나 | 무엇을 막나 |
|---|---|---|
| 1 | 이 작업 트리의 작업 기록 파일 | |
| 2 | 형제 워크트리의 작업 기록 파일 | 옆 세션이 아직 커밋하지 않은 번호 |
| 3 | 원격의 선점 ref 와 바닥 표시 | 다른 PC 가 방금 잡은 번호 |
| 4 | 원격 기준 브랜치에 커밋된 작업 기록 파일 | 내 체크아웃이 아직 모르는 번호 |

4 가 없던 때 실제로 겹쳤다. ref 없이 만들어진 문서(플러그인을 붙이기 전의 문서, 손으로 만든 문서)는 3 에 없고, 체크아웃이 뒤처져 있으면 1 에도 없다.

| 원격 dev 에 1~20 (ref 없음), 체크아웃은 1~10 시점 | 받은 번호 |
|---|---|
| 4 가 없을 때 | `0011` — 이미 원격에 있는 번호 |
| 4 를 넣은 뒤 | `0021` |

기준 브랜치를 정하지 못하면 번호를 주지 않는다. 아래 「기준 브랜치」 절을 본다.

## 설치

```bash
claude plugin marketplace add https://github.com/JahyunBaek/team-task-plugins
claude plugin install task-id@team-task-plugins
```

깃허브가 아닌 git 호스트에 올렸다면 **주소 끝에 `.git` 을 붙인다.** 안 붙이면 CLI 가 git 저장소가 아니라 JSON 파일 주소로 보고 HTTP 로 받으려 한다. AWS 코드커밋 주소가 그렇다 — `.../v1/repos/<이름>` 그대로 넣으면 `HTTP 401 error while downloading marketplace` 로 실패하고, `.../v1/repos/<이름>.git` 으로 넣으면 clone 으로 받는다.

## 쓰는 법

```
/task-new <도메인> <이름>
```

발급된 번호로만 파일을 만든다. 결과의 `attempts` 가 2 이상이면 그 사이 다른 세션이 번호를 채갔다는 뜻이다.

```json
{"ok":true,"id":"TASK-2026-core-0042","attempts":2,"path":"docs/tasks/core/TASK-2026-core-0042-...md","scanned":{"worktrees":1,"remote":true,"branch":"refs/heads/main"}}
```

## 설정

저장소 루트에 `.task-id.json` 을 두면 바뀐다.

| 키 | 기본값 | 뜻 |
|---|---|---|
| `taskDir` | `docs/tasks` | 작업 기록이 쌓이는 폴더 |
| `refNamespace` | `refs/task-ids` | 선점한 번호의 ref 를 두는 이름공간 |
| `remote` | `origin` | 판정을 맡길 원격 |
| `defaultBranch` | (자동) | "이미 커밋된 번호"를 판단하는 기준 브랜치. 발급·정리·안전망이 함께 쓴다. 예: `refs/heads/dev` |
| `digits` | `4` | 번호 자릿수 |
| `offlinePolicy` | `block` | 원격을 못 볼 때 — `block`(중단) 또는 `warn`(경고 후 잠정 발급) |
| `pruneKeep` | `20` | 정리할 때 개별 ref 를 남겨 두는 최근 번호 개수 |
| `maxAttempts` | `25` | 거절당했을 때 다음 번호로 넘어가는 최대 횟수 |

## 구성

| 조각 | 하는 일 |
|---|---|
| `/task-new` 커맨드 | 번호를 선점하고 발급한다 |
| `guard` 훅 (PostToolUse) | **새로 만든** 작업 기록 파일만 본다. 폴더와 번호의 도메인이 다를 때, 같은 번호의 문서가 이미 있을 때(이 트리 · 형제 워크트리 · 원격 기준 브랜치), `/task-new` 로 받은 번호가 아닐 때 알린다. 막지 않는다 |
| `/task-id-prune` 커맨드 | 쓸모를 다한 ref 를 원격에서 정리한다. 기본은 조회만 한다 |
| `task-id` 스킬 | 규칙과, 거절·망 끊김 때의 행동 |

## 기준 브랜치

"이미 커밋된 번호"는 기준 브랜치 하나를 보고 판단한다. 원격이 기본 브랜치를 알려주면 그것을 쓰는데, **코드커밋은 알려주지 않는다.**

```
깃허브:    ref: refs/heads/main	HEAD
코드커밋:  8f669ad...	HEAD          ← ref: 줄이 없다
```

그때는 로컬에 적힌 `origin/HEAD`, 그래도 없으면 HEAD 해시와 일치하는 브랜치를 쓴다. 다 실패하면 번호를 주지 않고 설정하라고 알린다.

실제 작업이 기본 브랜치가 아닌 곳(예: `main` 은 배포용, 작업은 `dev`)에 쌓이면 못박아 둔다.

```json
{ "defaultBranch": "refs/heads/dev" }
```

### 동시 발급과 fetch

기준 브랜치의 파일 목록을 보려면 그 커밋이 로컬에 있어야 한다. 처음에는 평범하게 `git fetch` 를 했는데, 여러 세션이 동시에 발급하면 추적 브랜치(`refs/remotes/origin/dev`)를 갱신하다 잠금끼리 부딪혔다.

| dev 를 움직이며 6개씩 동시에 5번 발급 (30회) | 성공 | 실패 | 겹친 번호 |
|---|---|---|---|
| 평범한 `git fetch` | 9 | 21 (`cannot lock ref`) | 0 |
| 지금 방식 | 30 | 0 | 0 |

지금은 `ls-remote` 로 끝 커밋의 해시를 먼저 묻고, 그 커밋이 로컬에 없을 때만 객체를 가져온다(`--refmap=` `--no-write-fetch-head`). 추적 브랜치와 `FETCH_HEAD` 를 건드리지 않으니 부딪힐 곳이 없고, 사용자의 `origin/dev` 를 몰래 움직이지도 않는다.

## 맞바꿈

- 발급할 때마다 원격을 탄다(ref 목록, 기준 브랜치의 끝 커밋, 선점). **원격을 못 보면 번호를 주지 않고 멈춘다**(기본값 `block`).
  다른 PC 가 무슨 번호를 잡았는지 모르는 상태이기 때문이다. 어차피 그 상태에서는 작업을 푸시하지도 못한다.
  정말 끊긴 채로 받아야 하면 `offlinePolicy` 를 `warn` 으로 두면 근거 1·2 만으로 **잠정** 번호를 준다.
- 선점해 놓고 문서를 쓰지 않으면 그 번호는 빈다.
- ref 는 저절로 지워지지 않는다. `/task-id-prune` 으로 정리하는데, 손으로 불러야 한다.

## ref 정리

```
/task-id-prune              # 조회만 한다
/task-id-prune --apply      # 실제로 지운다
/task-id-prune --keep 0 --domain core --apply
```

정리는 **파일이 기준 브랜치에 커밋된 번호의 ref 만** 지운다. 그 번호는 「번호를 정하는 근거」 4 가 계속 막는다.

여기에 한 겹을 더 둔다. 정리할 때 그룹(연도·도메인)마다 **"여기까지는 이미 쓰였다"** 를 ref 이름에 적어 하나 남긴다.

```
refs/task-ids/_floor/TASK-2026-cm-0020
```

발급은 이 번호도 읽는다(근거 3). 커밋된 문서가 나중에 지워지거나 이름이 바뀌어도, 기준 브랜치를 바꿔도 번호가 내려가지 않는다. **바닥 표시를 먼저 세우고 나서 지운다** — 순서가 바뀌면 그 사이가 빈다. 바닥 표시를 세우지 못한 그룹은 지우지 않는다.

바닥 표시는 근거 4 보다 먼저 만들었다. 그때 정리 뒤에 뒤처진 체크아웃이 `0011`(이미 있는 번호)을 받는 것을 재현했고, 바닥 표시를 넣은 뒤 같은 상황에서 `0021`, 21~30 을 커밋하고 다시 정리한 뒤 `0031` 을 받았다. 두 번째 정리에서 바닥 표시는 0020 → 0030 으로 올라가고 옛 표시는 지워졌다.

**지우지 않는 것이 두 가지다.**

- **파일이 아직 기준 브랜치에 없는 번호** — 지우면 그 번호가 다시 풀린다. 다른 PC 에 푸시하지 않은 초안이 있으면 같은 번호가 두 번 나간다.
- **최근 `pruneKeep` 개**(기본 20) — 여유분이다. `--keep 0` 이어도 안전하다.

정리하고 나면 그룹마다 ref 가 바닥 표시 하나로 줄어든다. 20개를 정리했을 때 원격에는 `_floor/TASK-2026-cm-0020` 하나만 남았다.

### 용량 이야기는 기대하지 않는 게 좋다

실측값이다. 작업 기록 파일 30건이 커밋된 저장소에 ref 33개를 만들어 두고 29개를 지웠다.

| | 값 |
|---|---|
| 원격 저장소 크기 | 35,317 → 34,543 바이트 (774바이트 줄었다) |
| ref 하나당 | 약 27바이트 |
| ref 가 가리키는 커밋 객체 | 123바이트 (압축 전) |
| 목록에 찍히는 한 줄 | 73바이트 |

**500개를 모아도 13KB다.** 줄어드는 쪽은 발급할 때마다 읽어 오는 목록 길이인데 그것도 500개면 36KB다. 아래 표의 Gerrit 은 252,633개를 달고 돌아간다. 정리는 깔끔함을 위한 것이고 용량 때문이 아니다.

## 이 방식이 안전한 근거

깃 공식 문서(`git update-ref`)가 "없을 때만 만들기"를 보장한다.

> 생성하려는 ref 가 존재하지 않음을 보장하려면 `<old-oid>` 에 40개의 "0" 또는 빈 문자열을 지정할 수 있다

같은 문서에 *"각 ref 는 개별적으로 원자적으로 갱신되거나 삭제된다"* 고 적혀 있다.

평범한 `git push` 도 이미 있는 ref 를 대개 거절하지만 이유가 다르다. 평범한 push 는 "새 커밋이 기존 커밋의 자손이 아니라서" 거절하고, `--force-with-lease=<ref>:` 는 "그 ref 가 존재해서" 거절한다. 새 커밋이 기존 커밋의 자손이면 평범한 push 는 덮어쓴다. 실제로 A 가 잡은 ref 에 A 의 자손 커밋을 밀었더니 평범한 push 는 B 로 바꿨고, `--force-with-lease=<ref>:` 는 `stale info` 로 거절해 A 를 지켰다.

## 이렇게 쓰는 곳들

`refs/` 밑에 자기 칸을 파는 것은 흔한 방식이다. 공개 저장소를 직접 조회한 결과다(2026-10-01).

| 저장소 | 자기 칸 | 개수 | 브랜치 |
|---|---|---|---|
| [Gerrit](https://gerrit.googlesource.com/gerrit) | `refs/changes/*` | 252,633 | 58 |
| [GitLab](https://gitlab.com/gitlab-org/gitlab-foss) | `refs/environments/*` · `refs/merge-requests/*` | 44,034 · 950 | 4,469 |
| [GitHub](https://github.com/anthropics/claude-plugins-official) | `refs/pull/*` | 5,142 | 718 |
| [git-bug](https://github.com/git-bug/git-bug) | `refs/bugs/*` · `refs/identities/*` | 454 · 312 | 33 |

깃 자체도 그렇다. `git notes` 는 `refs/notes/*`, `git stash` 는 `refs/stash` 를 쓴다.

**선점 용도로 쓴 사례도 있다.** [Backlog.md 의 제안](https://github.com/MrLesk/Backlog.md/issues/937)은 여러 사람이 같은 작업을 동시에 집는 문제를 `refs/backlog/tasks/*` 와 `--force-with-lease` 로 푼다. 목표를 *"동시 선점자는 정확히 한 명"* 으로 적고 있다. 다만 그쪽은 원격을 못 볼 때 **막는 쪽**을 택했고, 이 플러그인도 같은 선택을 기본값으로 둔다.
